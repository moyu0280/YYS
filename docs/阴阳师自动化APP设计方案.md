# 阴阳师日常/活动自动化 APP 设计方案

> 定位：单账号、屏幕级 UI 自动化智能体（Agent）
> 硬约束：**不读取游戏内存**、不注入、不修改游戏包、不需要 Root
> 技术路线：Android 无障碍服务（AccessibilityService）+ AI 决策

## 1. 产品定位与边界

| 项 | 说明 |
|---|---|
| 目标 | 用无障碍 + AI 完成一个号的日常与活动，人在挂机 |
| 硬约束 | 只用屏幕 + 无障碍"看/点"；不读内存、不 Hook、不改包；**禁用系统返回键**，返回一律点游戏内箭头/X |
| 定位 | 屏幕级 UI 自动化 Agent，本质是"会看会点的机器人"，不是外挂/修改器 |
| 单账号 | 只服务一个账号，不做多开/批量，降低风险面 |

**核心哲学**：把"玩游戏"变成"读屏幕 → AI 判断 → 无障碍点击"的闭环，游戏本身完全不变。

---

## 2. 合规与风险（必须明示）

1. **封号风险**：自动化可能违反网易《阴阳师》用户协议，存在账号被处罚的可能。本设计只解决"怎么做"，不承诺"不被封"。
2. **无障碍滥用**：Android 无障碍是辅助残障人士的能力，自动化游戏属于灰色用途，App 需在首次引导里明确用途并取得用户授权。
3. **隐私**：屏幕截图/OCR 内容可能包含昵称、聊天等，需默认本地处理，上传云端模型前脱敏。
4. **建议边界**：限制每日运行时长、加随机拟人化延迟、不做 PVP 冲分等高风险行为。

## 3. 总体架构（分层）

```
┌─────────────────────────────────────────────┐
│  交互层  Android AccessibilityService         │  ← 手：点击/滑动/输入/返回
├─────────────────────────────────────────────┤
│  感知层  UI树解析 + OCR + 截图VLM             │  ← 眼：看懂屏幕
├─────────────────────────────────────────────┤
│  认知层  AI Agent（观察→决策→执行→验证）        │  ← 脑：决定下一步
├─────────────────────────────────────────────┤
│  编排层  任务状态机 / 任务DSL / 每日调度        │  ← 计划：先做什么后做什么
├─────────────────────────────────────────────┤
│  知识层  任务库·屏幕词典·活动模板·领域知识(RAG) │  ← 记忆：玩法 + 最新版本内容
├─────────────────────────────────────────────┤
│  基础设施 日志 · 截图回放 · 重试 · 安全策略      │
└─────────────────────────────────────────────┘
```

**关键点**：感知、认知、执行三层构成一个循环，任何一层都能独立替换。

## 4. 核心模块设计

### 4.1 无障碍执行器（Executor，手）
基于 `AccessibilityNodeInfo` 封装原子动作：
- `click` / `longClick`（元素级）
- `swipe` / `scroll`（手势回放，Path 轨迹）
- `type`（文本输入）
- `wait`（等待）

> ⚠️ **禁用系统返回键**：`back`/`home`（系统级按键）被列为**禁止动作**，执行器不提供、代码层直接拦截，任何模块都无权调用。

**元素定位优先级**：`resource-id` > `text 文本` > `描述(desc)` > `坐标(OCR兜底)`。
优先用稳定的 id/文本，只有动态画面才降级到坐标点击，减少"点错"。

**返回/关闭策略（全部走游戏内 UI）**：
- 回上一页 → 只点游戏内 **左上角小箭头**；
- 关闭弹窗 → 只点 **右上角小 X**（或"关闭/取消"文字按钮）；
- 由「返回元素识别器」统一定位：优先 resource-id/文本，其次按屏幕区域（左上角、右上角）+ 图标形状识别兜底；
- 兜底顺序：页内回退箭头 → 页内"关闭/取消"按钮 → 都找不到则**暂停并交人工**，绝不降级到系统返回键。

> 返回识别器落地设计见 [`返回识别器详细设计.md`](./返回识别器详细设计.md)。

### 4.2 屏幕感知（Perception，眼）
三层递进，成本从低到高：
1. **UI 树结构化**：把无障碍节点树抽成"可点击元素列表"（id/文本/坐标），成本最低、最稳。
2. **OCR 兜底**：UI 树读不到文字时（如图片、特效、动态页），用 OCR 识别。
3. **截图 + 多模态 VLM**：复杂/陌生/活动页（战斗结算、新活动入口），截图交给多模态大模型理解，返回结构化"这是什么页面 + 有哪些可操作点"。

输出统一成一份 `ScreenState`（JSON）：页面类型、可用操作列表、置信度。

### 4.3 AI 决策（Brain，脑）
采用 **ReAct 式 观察→决策→行动→验证** 循环：

```
loop:
  screen = perceive()            # 读屏，结构化
  if is_terminal(screen): break
  action = llm.decide(screen, task, memory)   # 决定下一步
  executor.do(action)            # 无障碍执行
  screen2 = perceive()           # 再读屏验证
  memory.update(action, screen2) # 记录结果
```

**规则优先 + AI 兜底**的双轨策略：
- 确定性步骤（签到、领体力、打固定副本）走 **状态机/规则**，快、稳、省 token；
- 遇到**异常、弹窗、新页面、活动变化**时，才把上下文交给 LLM 决策，兜底处理。

**记忆**：
- 短期：当前任务上下文（已做过什么、当前在哪）；
- 长期：账号状态、活动进度、上次失败原因（持久化，供下次参考）。

### 4.4 任务引擎（Task Engine，计划）
- 每个"玩法"是一个**任务**（DAG/序列 + 前置条件 + 刷新时间）。
- 每日总流程按 **时间/依赖** 编排：例如先签到领体力 → 悬赏 → 御魂 → 探索 ……
- 能力：失败重试、断点续跑、单任务独立运行、手动介入（人接管后继续）。
- 阴阳师每日 **05:00 刷新**，调度以此为界。

### 4.5 任务库（知识层，记忆）
每个玩法一段 **YAML 配置 + 可选 AI prompt**，用户/社区可扩展新活动模板。

### 4.6 阴阳师领域知识（版本感知的 AI）

**目标**：让 AI 始终"知道最新版本阴阳师的所有内容"。不建议从零"训练"一个阴阳师大模型——成本高、且跟不上每周版本更新；改用 **「知识库 + RAG + 版本管理」** 的领域知识注入方案：

1. **结构化知识库（精确、可执行）**
   - 界面元素词典：每页/每玩法的 `resource-id`、文本、坐标区域、返回键类型；
   - 任务流程库：所有日常/活动的完整操作序列（即 4.5 的 DSL）；
   - 版本特性表：新玩法、新式神、新活动入口与规则。
2. **非结构化知识库（理解、兜底）**
   - 官方更新公告、活动公告、wiki、社区攻略 → 切片 + 向量化，供 RAG 检索；
   - 决策时把"当前版本相关片段"注入 prompt，让模型"懂"最新玩法。
3. **版本管理（保鲜机制，关键）**
   - 自动读取游戏版本号（登录页 / 设置-关于），识别当前版本；
   - 知识库按版本打标；版本更新时触发**知识刷新流水线**：抓公告 → 更新词典/流程库 → 标记旧版本条目失效；
   - 新活动上线 → 快速产出活动模板（规则为主 + AI 兜底）。
4. **微调（可选增强，非主路径）**
   - 可用历史"截图+决策"数据对本地小模型轻量微调，降低云端依赖；
   - 但"记住最新内容"永远靠知识库保鲜，微调模型不承担此职责。

> 结论：`RAG(知识库) + 结构化词典 + 版本流水线` 才是"知道最新版本所有内容"的正确打开方式；"专门训练"仅作可选加速项。
> 落地级表结构与保鲜流水线见 [`领域知识层详细设计.md`](./领域知识层详细设计.md)。

## 6. 技术选型

| 层 | 选型建议 |
|---|---|
| 前台 App | Android / Kotlin，内嵌 AccessibilityService |
| OCR | ML Kit 中文 / PaddleOCR（本地） |
| 多模态 | Qwen2.5-VL / GPT-4o / Claude（可选云端） |
| 决策 LLM | 通用 LLM API，或本地小模型（Ollama/Qwen）做离线模式 |
| 编排 | Kotlin Coroutines + 自研状态机 |
| 配置 | YAML/JSON 任务 DSL |
| 存储 | 本地 SQLite（日志、账号状态、截图回放） |

**两种运行模式**：
- **本地模式**（隐私优先）：OCR + 本地小模型决策，不联网，但理解力弱；
- **云端模式**（智能优先）：接多模态大模型，理解力强，需脱敏后上传截图。

## 7. 关键流程示例

### 7.1 每日总流程
```
05:00 刷新 → 签到 → 领免费体力/勾玉 → 悬赏封印
→ 结界突破 → 御魂 → 探索 → 百鬼 → 逢魔之时
→ 寮任务/捐赠 → 报告完成情况（哪些成功/失败/需人工）
```

### 7.2 单任务 DSL 示例（每日签到）
```yaml
task:
  id: daily_signin
  name: 每日签到
  schedule: daily          # 每日 05:00 后运行一次
  steps:
    - find: { text: "签到" }        # 主界面找签到入口
      action: click
    - wait: { until: { text: "领取" } }
      action: click
    - verify: { text: "今日已签到" }  # 校验成功
  fallback:
    ai: "找不到签到入口时：返回主界面，检查是否有弹窗遮挡，再重试"
```

### 7.3 Agent 提示词骨架（AI 兜底）
```
你是《阴阳师》自动化助手。当前任务：{task.name}
当前屏幕（已结构化）：{screen.json}
已完成步骤：{memory.done}
请判断当前处于什么页面，并给出下一步：
返回 JSON：{"page": "...", "action": {"type": "click|swipe|back", "target": "..."}, "reason": "..."}
仅基于屏幕信息决策，不要臆测。
```

## 8. 数据与安全

- **不接触账号密码**：登录、支付、验证码由用户手动完成，App 只操作"游戏内已登录状态"。
- **截图脱敏**：上传云端前可对昵称/聊天/数字做打码。
- **本地日志**：运行记录、截图回放存本地，供排查；默认不自动外传。
- **执行护栏**：危险操作（购买、充值、消耗稀有道具、删除）一律暂停并请求人工确认。

## 9. MVP 路线图

1. **MVP（规则驱动）**：签到 + 悬赏 + 结界突破 + 御魂，纯状态机 + UI 树定位，先跑通闭环。
2. **V2（AI 兜底）**：引入 OCR + LLM 处理异常/弹窗/未知页面，接入云端多模态。
3. **V3（全日常 + 活动）**：补齐全日常任务，做活动模板系统 + 云端任务库，支持用户自定义。
4. **V4（体验）**：拟人化延迟、运行报告、截图回放、断点续跑、手动接管。

---

## 10. 结论

这套方案的核心是：**无障碍当手、屏幕识别当眼、LLM 当脑、任务引擎当计划**，四层解耦。因为完全不碰内存，技术上"干净"，但它本质上仍是游戏自动化，**无法消除封号与违反 ToS 的风险**。建议先做 MVP 验证闭环，再逐步加 AI 能力。

## 11. 迭代与持续优化

本 App 是长期迭代项目，优化点持续沉淀在 [`迭代优化清单.md`](./迭代优化清单.md)，按 P0/P1/P2 分级、随版本滚动更新。三条主线：
- **稳定**：返回键/弹窗/加载容错、断点续跑、失败自愈；
- **智能**：版本保鲜、元素漂移自愈、模型路由、失败学习；
- **安全**：拟人化、时长限制、危险操作护栏、异常熔断。
