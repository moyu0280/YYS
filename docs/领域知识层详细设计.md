# 领域知识层详细设计（版本感知 AI）

> 对应主方案 §4.6。目标：让 AI 始终"知道最新版本阴阳师的所有内容"，并能随版本更新快速保鲜。
> 原则：**结构化知识负责"精确执行"，非结构化知识负责"理解兜底"，版本管理负责"保鲜"。**

---

## 1. 总体结构

```
                 ┌─────────────────────────────┐
                 │        决策 Agent（LLM）      │
                 └──────────────┬──────────────┘
                                │ 检索注入（RAG）
                 ┌──────────────▼──────────────┐
                 │        知识访问层（API）      │
                 │  按 版本 + 页面 + 任务 取知识  │
                 └──────────────┬──────────────┘
        ┌───────────────┬───────┴────────┬──────────────┐
        ▼               ▼                ▼              ▼
   结构化知识        非结构化知识       版本元数据      知识刷新流水线
  页面库/元素词典    公告·攻略·wiki    版本表/活动表    抓取→清洗→结构化→发布
  任务流程/特性表    (切片+向量)        (对齐/失效)
```

## 2. 数据结构（核心表）

### 2.1 版本与活动元数据

```yaml
game_version:
  version_code: "1.0.86"        # 客户端版本号（主键之一）
  build: "20251015"
  detected_at: 2025-10-15       # 首次识别时间
  valid: true                   # 知识是否仍对齐
  note: "十月第二期活动版本"

activity:                        # 限时活动
  activity_id: "act_2025_qingming"
  name: "清明活动"
  start_at / end_at             # 活动起止时间
  version_range: ["1.0.86", ]   # 适用版本
  task_flow_ids: [...]          # 关联任务流程
  status: upcoming|active|ended
```

### 2.2 页面库 page（识别"我在哪"）

```yaml
page:
  page_id: "p_yuhun_select"      # 御魂副本选择页
  name: "御魂-选择"
  # 识别指纹：命中若干即判定为当前页
  fingerprint:                   # 特征文本/节点组合
    must_text: ["御魂", "十层"]
    any_text: ["挑战", "御魂"]
    resource_ids: ["com.netease.onmyoji:id/..."]
  entry: "主界面→探索→御魂"      # 从主界面如何到达
  back_action: "arrow_top_left"  # 本页返回方式（见返回识别器）
  version_range: ["1.0.80", ]    # 哪些版本下此指纹有效
```

### 2.3 元素词典 ui_element（精确点击对象）

```yaml
ui_element:
  element_id: "e_yuhun_start"
  page_id: "p_yuhun_select"
  role: button|arrow_back|close_x|input|tab|item
  locate:                         # 定位优先级由高到低
    resource_id: "com.netease.onmyoji:id/btn_start"
    text: "挑战"
    desc: null
    region: {x: 0.5, y: 0.82, w: 0.3, h: 0.06}   # 相对坐标区域（机型无关）
  version_range: ["1.0.80", ]     # 失效即不再用
  last_verified: "1.0.86"         # 最近验证通过的版本
  status: active|stale|unknown    # unknown→触发自愈
```

### 2.4 任务流程 task_flow（可执行步骤）

```yaml
task_flow:
  task_id: "daily_yuhun"
  name: "每日御魂"
  version_range: ["1.0.80", ]
  preconditions:                 # 前置：体力>=6、已解锁、无弹窗
    - {type: stamina, min: 6}
    - {type: no_popup}
  steps:                         # 引用 page/element，而非硬编码坐标
    - enter: p_yuhun_select
    - action: {click: e_yuhun_start}
    - wait: {page: p_yuhun_battle}
    - action: {click: e_auto_battle}
    - wait: {page: p_yuhun_reward}
    - action: {click: e_reward_close}   # 点右上角 X，不用系统返回
  fallback_ai: "打不过/异常时：..."      # AI 兜底 prompt
```

### 2.5 非结构化知识 doc_chunk（理解兜底）

```yaml
doc_chunk:
  chunk_id: "c_act_qingming_001"
  source: "官方公告"             # 公告/wiki/社区攻略
  url: "https://..."
  version_range: ["1.0.86", ]
  text: "清明活动期间，完成……"
  embedding: [...]              # 向量
  tags: ["活动", "清明", "悬赏"]
```

## 3. 版本识别与对齐（保鲜的开关）

**读版本号途径**（按可靠性排序）：
1. 登录页左下/右下角版本号文本（OCR）；
2. 游戏内「设置 → 关于」里的版本号（UI 树/OCR）；
3. 主界面截图交给 VLM 询问"当前版本号"。

**对齐策略**：
- 启动任务前先 `detectVersion()`，与知识库 `game_version` 比对；
- 完全一致 → 正常；仅 `build` 不同（热更/资源更新）→ 沿用结构，标记"待观察"；
- `version_code` 变化 → **暂停任务**，进入知识刷新流程，提示用户"检测到新版本，正在更新知识库"。

**失效标记**：
- 版本升级后，旧版本条目不删除，而是把 `version_range` 不包含当前版本的条目标 `stale`；
- 运行时若某元素定位连续失败 N 次，标 `unknown` 并触发自愈（见 §5）。

## 4. RAG 决策注入流程

决策 Agent 每步请求知识时的检索顺序：

```
1. 精确命中：version + page_id → 取该页元素词典 + 当前任务 step
2. 语义检索：把「当前屏幕文本 + 任务目标」向量化 → 检索 doc_chunk（按版本过滤）
3. 组装 prompt（示例）：
   [系统] 你是阴阳师自动化助手，当前版本 1.0.86。
   [知识] 本页"御魂-选择"可用操作：点击"挑战"→进入战斗…
   [检索] 相关说明：十层掉落…（RAG 片段）
   [屏幕] {ScreenState JSON}
   [任务] {task_flow 当前步骤}
   → 输出下一步 action JSON
```

> 关键：**结构化知识直接给答案，RAG 只补充"为什么/特殊情况"**，避免让大模型自由发挥导致点错。

## 5. 知识刷新流水线（自动保鲜）

```
触发（定时 每日 + 版本变更事件）
   │
   ├─ 1. 抓取：官方公告/更新日志、wiki 页面、社区攻略（RSS/爬虫/手动提交）
   ├─ 2. 清洗：去广告、去水印、时间戳对齐版本
   ├─ 3. 结构化提取（LLM 辅助）：
   │       公告 → 新活动/新玩法/新入口 → 生成 activity + 特性条目
   │       攻略 → 步骤序列 → 生成 task_flow 草稿（人工复核）
   ├─ 4. 词典自愈：版本升级后对 stale/unknown 元素，
   │       用"截图+VLM 重新定位"回写 ui_element 的 resource_id/region
   ├─ 5. 校验：在真机/模拟器跑一遍关键任务，通过才置 active
   └─ 6. 发布：更新 game_version.valid，标记旧条目 stale
```

**元素漂移自愈**（重点）：版本更新最常见的坑是 id/文本变了。流程：
- 运行时发现某 `ui_element` 连续定位失败 → 标 `unknown`；
- 后台流水线在对应页面截图 → VLM 目标检测"哪个是'挑战'按钮/返回箭头" → 回写坐标/新 id；
- 下次运行直接命中，实现"版本更新不用人工逐条改"。

## 6. 冷启动与初始化（首次建库）

1. **人工标注种子**：先手动录一遍核心日常（签到/悬赏/御魂），采集页面指纹 + 元素 + 流程，作为种子数据；
2. **自动采集扩量**：跑任务时把每次读屏结果落库，未识别页面自动新增为"待标注"；
3. **批量导入**：wiki/攻略导入切分，建立非结构化知识；
4. 达到"核心日常可自动跑通"即视为冷启动完成。

## 7. 存储与实现选型

| 项 | 建议 |
|---|---|
| 结构化知识 | SQLite（本地，随 App）；远期可加服务端同步 |
| 向量存储 | 本地 `sqlite-vec` / 或接云端向量库（若走云端模型） |
| 检索 | 结构化精确查询 + 向量 Top-K（按版本过滤 + rerank） |
| 结构化提取 | 通用 LLM + 固定 JSON Schema 输出 |
| 更新流水线 | 服务端定时任务（若做云端任务库）；纯本地则手动/半自动触发 |
| 版本号识别 | OCR（ML Kit/PaddleOCR）+ VLM 兜底 |

---

## 8. 落地优先级

1. **P0**：`game_version` / `page` / `ui_element` / `task_flow` 四张表 + 版本对齐逻辑 —— 先让"精确执行"跑起来；
2. **P0**：元素定位优先级 + `stale/unknown` 状态机；
3. **P1**：doc_chunk + 向量检索，接入 RAG；
4. **P1**：知识刷新流水线（抓取 + LLM 结构化 + 自愈）；
5. **P2**：云端任务库与社区共建。
